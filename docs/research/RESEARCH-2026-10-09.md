# Research: hardening a multi-lane Claude Code setup (2026-10-09)

Scope: one developer, a coordinator session plus several worktree "lanes", a fresh-context verifier,
merge scripts with a 45-minute window, user-level hooks, auto mode, legacy AWS SSO, and multi-hour
ops scripts on a laptop. Every source below was read on 2026-10-09; keys like [CC-hooks] map to the
Sources list at the end. "Secondary" marks a claim that comes only from a vendor or third-party page.
"Own recommendation" marks engineering judgment with no external source.

Verdicts: **ADOPT** (do now, small), **LATER** (worth it, not urgent or needs a trial), **SKIP**.
**[needs owner approval]** marks anything that changes permissions, approvals, IAM or third-party access.

## 1. Subagents, plugins, background and cloud sessions, headless, Action, routines

**Subagent definitions** ([CC-subagents]). Frontmatter seen in the docs: `name`, `description`
(required); `tools`, `disallowedTools`, `model` (`sonnet`/`opus`/`haiku`/`fable`/full ID/`inherit`),
`permissionMode`, `isolation` (accepts only `worktree`), `background`, `effort`
(`low`…`max`), `maxTurns`, `skills`, `memory` (`user`/`project`/`local`), `mcpServers`, `hooks`,
`omitClaudeMd`, `initialPrompt`, `color`, `experimental` (`cacheTtl`). Subagents can nest up to three
layers by default (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`). `isolation: worktree` branches "from your
default branch rather than the parent session's HEAD" and is removed if unchanged.
- ADOPT: turn the verifier pane into `~/.claude/agents/verifier.md` with `tools: Read, Grep, Glob, Bash`,
  `disallowedTools: Edit, Write`, and an explicit `model`/`effort`. The lane calls it with only the diff
  and criteria, which matches the "fresh-context review" rule and frees a pane. Keep a separate pane only
  for reviews that need a different human-visible transcript.
- LATER: `isolation: worktree` subagents for one-file fixes; they overlap with lanes and start from the
  default branch, which surprises stacked work.

**Background sessions / agent view** ([CC-agentview]). `claude --bg "<prompt>"`, `claude agents`,
`claude attach|logs|stop|respawn|rm <id>`, `claude daemon status`. A supervisor keeps sessions running
after the terminal closes and through sleep, but not through shutdown or restart. Sessions that need
input show "Needs input" and can be answered from a peek panel (`Space`) without attaching. Each
session moves into its own worktree under `.claude/worktrees/` before editing.
- LATER: trial one lane as `--bg`. It fixes the "which pane do I type the go in" friction because one
  agent view answers every lane, and the approval is still yours, typed in that session. Risk: it changes
  the Ghostty launcher workflow, and some dialogs still require attaching.

**Cloud sessions and routines** ([CC-routines], [CC-sched]). Routines run on Anthropic cloud from a
fresh clone, are triggered by schedule (min 1 h), API, or GitHub PR/release events, need the Claude
GitHub App for GitHub triggers, and run "without stopping for approval". Network is the default allowlist
unless the environment is changed; env vars are "visible to anyone who uses the environment".
- SKIP for the AWS ops jobs: they need laptop SSO credentials, and putting AWS keys in a cloud
  environment is an IAM decision [needs owner approval]. LATER for repo-only chores (stale PR sweeps).

**Headless** ([CC-headless]). `claude -p` with `--output-format json` (includes `total_cost_usd`),
`--json-schema`, `--max-budget-usd`, `--max-turns`, `--permission-mode`, `--permission-prompts none`
(v2.1.259+), `--bare`. Bare mode skips hooks, skills, agents, plugins, MCP and CLAUDE.md and needs
`ANTHROPIC_API_KEY`. Without `--bare`, a `-p` run executes the project's hooks "even in a folder you've
never trusted". SIGTERM exits 143 and leaves the turn unfinished.
- LATER: a capped `-p` call inside the merge script (for example "summarize the batch diff for
  conflicts") is cheap, but `--bare` drops the PreToolUse guard, so pass `--settings` explicitly.

**GitHub Action** ([CC-gha]). `anthropics/claude-code-action@v1`; inputs `prompt`, `claude_args`,
`anthropic_api_key` or `claude_code_oauth_token` (from `claude setup-token`), `settings`, `plugins`.
Costs Actions minutes plus tokens. Commits pushed with the default `GITHUB_TOKEN` don't trigger CI.
- LATER: a nightly scheduled run on main is the cleanest home for a semantic-conflict canary, but the
  batch script (section 4) catches the same failure before merge at no extra cost.

**Plugins** ([CC-plugins]). A directory with `.claude-plugin/plugin.json` bundling skills, agents,
hooks, MCP servers; load locally with `--plugin-dir`. "An enabled plugin is part of every session":
its skill and agent descriptions use context every turn.
- LATER: package only if the hooks and agents are shared with teammates.

## 2. Hooks

Events in the reference ([CC-hooks]) include `SessionStart` (matchers `startup`, `resume`, `clear`,
`compact`, `fork`), `PreToolUse`, `PostToolUse`, `PermissionRequest`, `PermissionDenied`, `Notification`
(matchers such as `permission_prompt`), `Stop`, `StopFailure`, `SubagentStart`/`SubagentStop`,
`WorktreeCreate`/`WorktreeRemove`, `PreCompact`/`PostCompact`, `FileChanged`, `SessionEnd`.

Exit codes: 0 means success and stdout JSON is read; **2 blocks "regardless of JSON output"** on
blocking events (`PreToolUse`, `Stop`, `SubagentStop`, `PreCompact`, …); any non-zero fails
`WorktreeCreate`; other codes are non-blocking. Output for `Notification`, `StopFailure`, `SessionEnd`
is ignored. JSON: `continue`, `stopReason`, `systemMessage`, `hookSpecificOutput` with
`permissionDecision` (`allow|deny|ask|defer`), `updatedInput`, `additionalContext`; `PermissionRequest`
uses `decision.behavior`; `PermissionDenied` can return `retry: true`. Output caps at 10,000 chars.
Timeouts: 600 s for command hooks (30 s on `UserPromptSubmit`), 30 s prompt, 60 s agent.

Performance and correctness ([CC-hooks-guide]):
- "Claude Code runs all matching hooks in parallel"; if several `PreToolUse` hooks return
  `updatedInput`, "the last one to finish takes effect", so only one hook may rewrite a tool.
- The `if` field takes permission-rule syntax (`"Bash(git *)"`) so a hook spawns only for matching
  calls. ADOPT on the Bash guard if it only cares about a few command families.
- Exec form (`"args": []`) "spawns the script directly without a shell". ADOPT for new hooks.
- Test a hook by piping JSON: `echo '{"tool_name":"Bash","tool_input":{"command":"ls"}}' | ./my-hook.sh`;
  `/hooks` lists what loaded; `--debug-file` logs execution. ADOPT as a small test file per hook (also
  "prove a check can fail": include one input that must exit 2).
- Stop hook: "Claude Code overrides a Stop hook after it blocks eight times in a row"; check
  `stop_hook_active` and exit early when true. A CI Stop hook also has to finish within the 600 s
  default timeout or set its own `timeout`. The reference lists `async` and `asyncRewake`
  ("Background with wake on exit 2"); docs I read are silent on the details, so trial before relying on it.

Security pitfalls ([CC-hooks], [CC-headless]): project hooks need workspace trust, but `-p` runs execute
project hooks without a trust dialog; hooks run with your credentials (`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1`
strips sensitive env vars); build JSON with `jq`, not string concatenation.

ADOPT, three small hooks:
1. `SessionStart` matcher `compact`: print the lane's ticket, branch, last pushed sha and any pending
   approval ask from a lane state file; plain stdout becomes context.
2. `PermissionDenied`: append `tool_name` + `tool_input` + reason to a log, so auto-mode false blocks
   are measured, not remembered.
3. `Notification` matcher `permission_prompt`: `osascript` notification naming the session, so a
   prompt in a hidden pane is seen.

## 3. Permissions and auto mode

Precedence ([CC-perms]): "deny, then ask, then allow. The first match in that order determines the
outcome, and rule specificity doesn't change the order." Bash rules split compound commands on `&&`,
`||`, `;`, `|`, `&` and newlines, and each part must match. They don't match other spellings:
`Bash(git push *)` doesn't catch `git -C . push`, `/usr/bin/…`, or `sh -c '…'`, so a rule "isn't a
security boundary around the program".

Auto mode ([CC-modes], [CC-automode]):
- Order: allow/ask/deny rules resolve first; content-scoped ask rules "always force a permission prompt,
  even in auto mode"; then read-only and in-worktree edits; everything else goes to the classifier.
- On entering auto mode, broad rules are dropped (`Bash(*)`, wildcarded interpreters, package-manager
  run commands, `Agent`, `Monitor`). **Narrow rules like `Bash(npm test)` stay in effect and skip the
  classifier.** The docs warn this "can still let a destructive argument through … for example a script
  path or flag the rule's prefix didn't anticipate". `autoMode.classifyAllShell: true` suspends every
  Bash allow rule while in auto mode.
- Blocked by default includes "Merging a pull request no human has approved", "Granting IAM or repo
  permissions", production deploys, force push, and "Writing to Claude Code session transcripts".
- `autoMode` fields: `environment`, `allow`, `soft_deny`, `hard_deny`, `classifyAllShell`. Read from
  `~/.claude/settings.json`, managed settings and `--settings` only; "The classifier doesn't read
  `autoMode` from project settings". An array without `"$defaults"` "replaces the entire default list".
  Inspect with `claude auto-mode defaults|config|critique|reset`.
- Thresholds: 3 blocks in a row or 20 total pause auto mode and fall back to prompting (not configurable).
- Approval wording: an approval must "name the action and its specifics"; it covers one action unless
  granted as standing.

**Why path-only allow rules on mutable scripts are risky.** Auto mode allows local edits in the
working directory, and a narrow allow rule bypasses the classifier. So `Bash(./scripts/merge.sh *)` approves
whatever the script contains at run time, including an edit the same session just made. Smallest fix
(ADOPT, [needs owner approval]): the existing PreToolUse guard computes `shasum -a 256` of any script named in an allow-listed
command and returns `permissionDecision: "ask"` if it differs from a pinned hash file kept outside the
worktrees. Alternative: `classifyAllShell: true`, which costs one classifier call per shell command.

**Merges and IAM under auto mode.** Don't loosen the classifier for merges or IAM. Add
`permissions.ask` entries for the merge command so a merge becomes an explicit keypress in that pane
[needs owner approval]. Keep IAM writes as human-run scripts. Cross-session messages can't approve
anything ([CC-xsession]), which is the behavior the "gos must be direct" rule relies on.

## 4. Merge queues for a solo developer

- **GitHub merge queue** ([GH-mq]): "available in any public repository owned by an organization, or in
  private repositories owned by organizations using GitHub Enterprise Cloud." So: not on a personal
  account, not on private repos under Free or Team. SKIP. (Workflows need the `merge_group` trigger.)
- **Rulesets / protected branches** ([GH-rulesets], [GH-protected]): on private repos they need Pro
  (personal) or Team/Enterprise (org); Free gets them only on public repos. Docs I read are silent on
  the plan of each repo here; check before relying on "require up to date before merging".
- **Mergify** ([Mergify-pricing], secondary, vendor page): free tier "Up to 5 active users (private
  repos)" including Merge Queue. Personal-account support: docs silent.
- **Trunk** ([Trunk-pricing], secondary): "Free for teams up to 5", merge queue included.
- **Graphite** ([Graphite-pricing], secondary): merge queue on Team ($40/user/month) and org repos only. SKIP.
- **bors-ng** ([bors]): archived; recommends GitHub's merge queue. SKIP.

**ADOPT: batch-branch script** (own recommendation). This is what a merge queue does, minus the hosting:
1. `git fetch`; create `batch/<UTC-timestamp>` from `origin/main` at a recorded sha.
2. Merge each ready PR head, by its announced full sha, in queue order. On a textual conflict, drop that
   PR and continue.
3. Run the **full local suite** (pytest, cfn-lint, JSON validator) on the batch head, then push the
   batch branch and wait for CI green on that exact sha.
4. If green and `origin/main` hasn't moved: `git push origin <batch-sha>:main`. A plain push is
   fast-forward only. If main moved, restart from step 1. If red, bisect by dropping the newest PR.
5. Check each PR shows as merged. I didn't verify in today's docs that GitHub marks a PR merged when its
   head commit reaches main by a direct push, so check this on the first batch and fall back to
   `gh pr close` with a comment naming the batch sha. Keep merge commits, not squashes, so PR heads
   stay in main's history.
This replaces several 45-minute waits with one CI run per batch, and it is the only option here that
catches semantic conflicts, because CI tests the combined result. Mergify or Trunk free tiers become
worth a trial (LATER, third-party app install [needs owner approval]) once there are more than a few
PRs a day.

## 5. AWS SSO for long jobs

- Legacy profile config: "your session is fixed at eight hours and cannot be refreshed automatically.
  When the session expires, any code that resolves new credentials fails authentication until you run
  `aws sso login` again. If you have long-running processes or automation, use the SSO token provider
  configuration" ([AWS-sdk-sso]). This matches the 4+ cut runs.
- `sso-session` config ([AWS-cli-sso]): `[sso-session NAME]` with `sso_start_url`, `sso_region`,
  `sso_registration_scopes = sso:account:access`; profiles reference it with `sso_session = NAME`. "A
  minimum scope of `sso:account:access` must be granted to get a refresh token" ([AWS-sdk-sso]). The
  CLI "automatically renews expired AWS credentials when needed" while the SSO session is valid. Needs
  AWS CLI v2 ≥ 2.9 and boto3/botocore ≥ 1.26.10 ([AWS-idc-cli]). Check the venv's botocore version.
- Ceilings: user interactive session default **8 hours**, configurable from 15 minutes to 90 days
  ([AWS-idc-interactive]); permission-set role sessions default 1 h, max 12 h ([AWS-idc-permset]); the
  CLI re-fetches role credentials while the SSO session lives.
- `aws configure export-credentials` ([AWS-export]): formats `process` (default, the `credential_process`
  schema), `env`, `env-no-export`, and others. Docs silent on whether it emits `Expiration`. If it does,
  `credential_process = aws configure export-credentials --profile X` lets other SDKs refresh, because
  with `Expiration` set credentials "are automatically refreshed by rerunning the `credential_process`
  command before the credentials expire", and the SDK "does not cache" process credentials ([AWS-process]).
  The `env` format is a one-time snapshot: a script that `eval`s it dies when those role credentials expire.
- ADOPT (local file only): convert the profile to `sso-session`, have long scripts use `AWS_PROFILE`
  instead of exported keys, and add a preflight that reads the SSO cache expiry under `~/.aws/sso/cache`
  and refuses to start a run that would outlive it. (Correction: under `sso-session` the cache `expiresAt` is
  the hourly, self-refreshing access token, not the session end; the preflight uses a recorded sign-in time
  plus the session length instead. See GROUNDING-PLATFORM-2026-10-09.md #11.) LATER [needs owner approval]: ask the admin for a
  longer interactive session.

## 6. Cost control

- Models ([CC-model]): aliases `sonnet`, `opus`, `haiku`, `fable`, `best`, `opusplan` (Opus to plan,
  Sonnet to execute). Default effort on Opus/Sonnet/Haiku 5.5 is `medium`; set with `/effort`,
  `--effort`, `CLAUDE_CODE_EFFORT_LEVEL`, `effortLevel`, or `effort:` in agent/skill frontmatter.
  `CLAUDE_CODE_SUBAGENT_MODEL` sets one model for all subagents. ADOPT per-agent `model:` instead, so a
  log-scanning agent can be `haiku` while the verifier keeps a strong model (accuracy first).
- Caching ([CC-costs]): cache lifetime "is an hour on a subscription and drops to five minutes once
  you're drawing on usage credits". **Surprise:** an idle lane waiting out a merge window while on usage
  credits reprocesses its full context on the next turn. Clear or compact lanes before long waits.
  `/usage` shows a `Prompt cache (main)` line with misses and likely cause (v2.1.251+).
- Visibility: `/usage` breaks usage down by skill, subagent, plugin, MCP server and `/loop` task, and
  flags behaviors at ≥10% ([CC-costs]). Statusline JSON includes `cost.total_cost_usd`,
  `context_window.used_percentage`, `rate_limits.five_hour.used_percentage`,
  `rate_limits.seven_day.used_percentage`, `rate_limits.spend_limit.*` ([CC-statusline]). OTel:
  `CLAUDE_CODE_ENABLE_TELEMETRY=1`, `OTEL_METRICS_EXPORTER=console|otlp|prometheus`, metrics
  `claude_code.cost.usage`, `claude_code.token.usage` with `session.id` and `model` ([CC-otel]).
- Context hygiene ([CC-costs]): `/clear` between unrelated tasks; keep CLAUDE.md under ~200 lines and
  move workflow detail into skills; idle sessions still spend on scheduled tasks, cross-session messages
  (`crossSessionInbound: hold` stops that) and goal check-ins.

## 7. Process watchers on macOS

- **pgrep self-match** ([man-pgrep]): macOS pgrep says "a running pgrep or pkill process will never
  consider itself as a potential match", and by default excludes "the current pgrep or pkill process and
  all of its ancestors" (`-a` includes them). So a `pgrep -f` watcher that "matched itself" was matching
  a non-ancestor whose argv contains the pattern: a sibling shell, the wrapper that launched the loop, or
  another copy of the watcher. On Linux procps the ancestor rule may differ (not checked). Matching on
  argv is fragile; `pkill -f` broadcasts the same fragility as SIGTERM, which is how 5 jobs died.
- **Use PIDs, not patterns**: write `$!` to a pidfile at launch; check liveness with `kill -0 "$pid"` or
  `pgrep -F pidfile` (`-L` requires the file to be locked); stop with `kill "$pid"` or `pkill -F pidfile`.
- **Done markers**: the job writes `<out>/DONE` (with exit code) as its last step; watchers wait on that
  file, never on process absence, because a crash and a success both make the process disappear.
- **Single instance**: macOS has no `flock(1)` but ships `lockf` ([man-lockf]):
  `lockf -k -t 0 /path/job.lock ./job.sh` fails at once if already running; "In no event will lockf
  break a lock that is held by another process."
- **Sleep**: `caffeinate -i ./job.sh` holds an idle-sleep assertion for the job's lifetime; `-s` prevents
  system sleep "only when system is running on AC power"; `-w PID` attaches to a running job
  ([man-caffeinate]). It doesn't help with network drops (retry reads instead).
- **nohup vs launchd**: nohup only ignores hangup. A LaunchAgent with `KeepAlive` → `SuccessfulExit=false`
  restarts a job that exits non-zero; "Jobs that exit quickly and frequently … will be throttled"
  ([man-launchd.plist]). LATER: only useful once jobs resume from done markers (item 8), otherwise a
  restart repeats work.
- **Inside Claude Code** ([CC-tools]): background Bash in a local interactive session has no time limit;
  in `-p`/SDK runs the default is 30 min, max 2 h. Monitor watches end after 5 min by default (max 30)
  and are for short watches only. For multi-hour jobs: launch detached with pidfile + DONE marker, and
  poll the marker with a `run_in_background` until-loop.
